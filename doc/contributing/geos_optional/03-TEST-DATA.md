# 3. The test data

**Measured at** MobilityDB master `d9b9c11985`.

Every claim in these notes rests on running the engine over a set of inputs and judging the
answers. This note lists those sets: where each comes from, what it holds, and what it can and
cannot tell. Row counts are read from the files.

## 3.1 Why there are so many

No single data set can judge a geometry engine, because the failures hide in different places:

- **Real data** finds what users meet: large polygons with thousands of vertices, coordinates in
  projected metres (around 600 000 east, 6 000 000 north), shapes with holes and many parts. It
  rarely contains the exact degenerate cases — two boundaries touching at one point, a segment
  lying exactly along another — where an algorithm is most likely to be wrong.
- **Generated data** targets those cases, and each generated set is built so that its exact
  answer is known by construction or decided by CGAL.
- **Test suites written by others** — GEOS's own — check the engine against assertions written
  independently of it.

Two more distinctions recur below:

- **A set that only contains queries the engine answers cannot see a new decline** (note 2,
  §2.5). Each set's *decline floor*, the number of its queries already declined, is stated with
  it.
- **A pass/fail regression test cannot tell a correct change from a wrong one** in a regime its
  fixtures do not reach. MobilityDB's SQL regression suite compares output with stored expected
  files; where no stored case reaches a change, it reports the same green either
  way. That is why the campaign judges with CGAL on the sets below, not with the regression suite.

## 3.2 How to read the tables below

Each table gives one data set per line. **Rows** counts the lines of the file: a pair of
geometries, a single geometry, a query or a record, as the second column says. A *query* is one
question asked of the engine, for example "is this point inside the buffer of that polygon at
that distance". Pull requests usually report *checks* rather than rows: one row can carry several
checks, for instance the four relationships of one pair of geometries, which is why a figure such
as "18 564 checks" in note 4 is larger than the 12 880 rows of its data set.

Three abbreviations recur. **AIS** is the Automatic Identification System, the positions ships
broadcast, the source of the vessel trajectories. **H3** is Uber's hexagonal grid of the Earth,
whose cells MobilityDB supports as a type. **Z** is the third coordinate (elevation) a geometry
may carry beside x and y, and **M** a measure value; a *Z mode* says which operands of a pair
carry Z.

## 3.3 Where the files are

The data sets and the probes are kept outside the repository, on the campaign's measuring
machine, and none of them runs in continuous integration today. One exception is already in the
tree: the GEOS relate suite (§3.4). Bringing the essential sets in is a step of the
[implementation plan](IMPLEMENTATION-PLAN.md). Each set below is named by its file name so a
reader can match it with the pull-request messages that cite it.

## 3.8 The inputs of the GEOS-free measurement

The programs of [`tools/`](tools/) that establish what still needs GEOS carry their inputs in their
source, so they need no data file. [`tools/geos_fallback_sweep.c`](tools/geos_fallback_sweep.c)
takes one small geometry of each of 15 types, each written flat and with Z, every collection of
two of them, and fifteen hand-written special cases (coinciding arcs, a fork, a line doubling
back, polygons sharing an edge or a corner, discs tangent at one point, a line of zero length,
and others). [`tools/merge_sweep.c`](tools/merge_sweep.c) merges two instants of every pair of those types,
as temporal geometries and as temporal geographies. [`tools/gateway_reach.c`](tools/gateway_reach.c) adds temporal points, temporal
geometries whose value is multi-part or a collection, and moving discs, against seven geometry
arguments. Their outputs are in [`tools/results/`](tools/results/).

## 3.9 The probes that judge them

A *probe* is a small C or C++ program that reads one of the sets, calls MEOS on each row, and
prints the answer in a form a judge reads. A *judge* computes the exact answer and compares.

| Probe | What it does |
|---|---|
| `perf_geos` | Times the native engine and GEOS 3.14 called directly, in one process, on the same rows; modes relate, buffer, union, distance |
| `cgal_segpairs` | Exact relationship of two segments: share nothing, one point, or a stretch |
| `cgal_arc_relate` | Exact predicates with circular arcs, using CGAL's exact circular-arc support |
| `cgal_linearea_ib` | Exact boundary-against-interior cell of a line and a polygon |
| `ib_judge` | Exact boundary/interior cells of two polygons |
| `accept_relate` | Three acceptance checks: a shape against itself, MEOS against GEOS without self-pairs, the shared area against CGAL |
| `cgal_linemeasure` | Exact length of the point set a line covers, counting a doubled stretch once |
| `cgal_uunion`, `cgal_zlift` | The union by the measure of its point set; the elevations an overlay carries |
| `cgal_buffer_arc`, `buf_ledger_cgal` | Whether a point is within the buffer distance of a shape, in exact arithmetic |
| `relate_diff` (in the tree) | Scores the GEOS relate suite |

Every probe carries a *control*: a case with a known answer that it must get right before its
other output counts, and for the judges a case it must get *wrong* when the answer is perturbed,
which shows the judge can fail. A judge that has never been seen to fail proves nothing.
